# Internationalisation: the options compared

How Skwir could be translated, and what has to change around the
translations: dates, numbers, sizes, name order, names the system gives,
right-to-left scripts, packaging and translators. Status: research,
2026-11-12; nothing is built and nothing is decided. Facts about
libraries, platforms and projects are as of that date. Measurements come
from throwaway benches on one loaded machine and are not kept in the
repository; they are marked where they appear.

## In short: turn Skwir's words into data first

The best route to internationalising Skwir starts with a change to its structure, before any library is chosen. Every piece of user-facing text becomes a typed, serialisable message: a crate's id plus typed arguments. Core defines that message type, each crate or plugin supplies the words from its own catalog, and the shell resolves the message into the user's language where it draws it. On top of that sit Project Fluent's FTL format for the messages, ICU4X for the numbers, dates, plurals and (later) name order around them, a small gettext domain for the `.desktop` and AppStream files, and Hosted Weblate for translators. The structure matters more than the library because Skwir's English already crosses every boundary as finished text. There are about 7,500 English literals and about 470 commands whose titles double as MCP tool metadata. Plans carry pre-rendered "Words" that are serialised to agents, the manifest of a plugin from outside is plain strings, and some code parses its own English back or joins two plugins' submenus by an English title. Among the formats, Fluent fits Skwir's engineering rules best: it is pure Rust on every system, supports one catalog per crate, can be loaded at run time by plugins from outside, lets translators rather than Rust code choose plural and noun forms, and has the closest Rust prior art in COSMIC and fish. gettext PO fits translators best, but it has no maintained pure-Rust loader, and its C binding brings LGPL autotools builds into the Windows and macOS packages. rust-i18n and translations written as code fail on plurals or on catalogs loaded at run time, and MessageFormat 2 has no Rust engine yet. gpui cannot mirror a layout for right-to-left languages today, so the first languages are left-to-right ones. Isolating right-to-left file names inside sentences is worth doing now, for English users too. Three costs are unmeasured: the memory and startup time of a loaded catalog, the cost per draw of resolving messages, and whether macOS and Windows draw Fluent's isolation marks invisibly. The first steps are an ADR and a refactor of the English code that pays for itself before a single string is translated.

## About 7,500 English strings cross every boundary already rendered

The audit found **about 7,500 English literals in non-test Rust code that read as human text**. About 5,000 are capitalised labels and sentences, and about 2,500 are lowercase phrases, mostly errors and sentence fragments; about 1,480 are `format!` templates. `crates/ui` holds about 2,550, the 42 plugin crates about 2,950 together, `crates/core` about 880, `crates/platform` about 620 and the worker crates about 350. Beside them sit 539 distinct descriptions in `crates/core/src/exclusions/builtin.toml` and a dozen packaging strings. A throwaway lexer written for the audit counted them; in a sample of 30 literals, about 95 % were user-facing. The figures count occurrences, so a catalog with duplicates removed would be smaller. Skwir has no catalog and no wording module. The few central places are `ui::format` (counts, sizes, dates), `ui::toast` (every plan's answer), `core::op::io_words`, `ui::placeholder` and `preview_bar::label`.

What makes Skwir harder than a typical application is that this text is data that travels. `CommandRegistry::register` takes `title: &str, description: &str` and stores them as `String`s (`crates/core/src/command.rs:519-533`). **About 470 commands** carry roughly 940 such strings, and each serves at once as palette label, F1 heading, MCP tool metadata and part of an agent's prompt. The control plugin builds each MCP tool straight from its `CommandSpec`, appending English to some descriptions (`crates/plugins/control/src/lib.rs:306-335`).

Plans carry English the same way. A plan's steps carry `op::Words { will, did, already }`: three pre-rendered English phrasings, `Serialize` and `JsonSchema`, that travel inside `PlanData` to agents and back (`crates/core/src/op/mod.rs:308-322`). 88 `Plan::new` sites pass lowercase English titles, and an undo's title is made by prefixing `format!("undo {}", …)` (`crates/core/src/op/executor.rs:4415`).

Settings (about 132 `SettingSpec` constructors), menu items and the manifest of a plugin from outside are English `String`s too. The manifest is read under `#[serde(deny_unknown_fields)]`, protocol `VERSION = 1`, and its `InitializeParams` sends no locale (`crates/plugin-api/src/manifest.rs:88-198`, `crates/plugin-api/src/protocol.rs:21`). Translating these strings where they are made would hand the user's language to agents. A plan written by an agent or a plugin from outside would still show in its author's language in the review. The design problem is the boundary, not the string count.

The sentences are built with English grammar:

- **Plurals.** `format::count` appends an `s` (`crates/ui/src/format.rs:68-75`) at 86 call sites. About 81 more places choose `""` or `"s"`, `was` or `were`, `it` or `them` by hand.
- **Fragments.** `system::not_yet` slots gerund fragments into `"{what} is not available on {NAME} yet"` at 28 sites (`crates/core/src/system.rs:18-25`). Errors are joined with `": "`.
- **Capitalisation.** Toasts reuse a lowercase plan title in several grammatical positions and capitalise it in code, with 32 calls of `toast::capitalized`.
- **Typography.** **673 interpolations hard-wire English curly quotes** (`“{…}”`), and 62 lists are joined with `", "`.
- **Numbers and dates.** Date formats embed English words inside strftime patterns. Sizes are divided by 1024 but labelled `KB`, and the thousands separator is a literal comma (`crates/ui/src/format.rs:118-129`).

Worse, some behaviour depends on the English itself, so translation would break it silently:

- **Text parsed back.** The toast undoes the executor's prefix with `title.strip_prefix("undo ")` (`crates/ui/src/toast.rs:228`, `:608`) and strips `"{name} could not "` to find a reason. The placeholder recognises a missing provider by `contains("no provider")`, and falls back to `contains("permission denied")` (`crates/ui/src/placeholder.rs:28-52`).
- **Plugins joined by English titles.** Independent plugins meet in one submenu by its English title: `"Tags"` from tags and name-tags (`crates/plugins/tags/src/lib.rs:676`, `crates/plugins/name-tags/src/lib.rs:463`), `"Compress"` from archives and shrink, `"Open With"` from shell and open-with. Settings sections are matched by their English heading (`crates/ui/src/settings.rs:1894`).
- **Labels derived from ids.** Sidebar group titles are capitalised from the group id, `keymap::title` falls back to the command id, Properties uses `label_of`, and `SettingSpec::data` uses the key as its title. A translated window would show these English ids.

Two plugins translated by different people would split one submenu into two. That is an invariant broken by translation, and AGENTS.md's "fix structurally" rule says to make such breakage impossible rather than patch it. Tests pin the English too: 335 assertions compare prose, and `crates/skwir/tests/settings.rs:128-170` enforces sentence case and a first sentence of at most 30 English words.

Some text already arrives in the user's language, which is why today's window mixes languages:

- **Desktop entries** are read as `Name[fr]` from `LC_ALL`, `LC_MESSAGES` or `LANG`, though not `LANGUAGE` (`crates/platform/src/apps.rs:375-418`).
- **Type names** come from the system, in the user's language, on macOS and Windows (ADR-037). On Linux, Skwir deliberately reads shared-mime-info's untranslated `<comment>`, although a current shared-mime-info's file for `text/plain` holds 34 translations (`crates/platform/src/mime.rs:263-278`).
- **Dialogs and errors.** GVfs and KDE dialogs speak the user's language, and the OS's error text passes through wherever `io_words` has no English of its own.

So a French user on macOS reads French type names inside English sentences today. Nothing in PLAN.md or the ADRs plans translation. The only decision that anticipates it is ADR-054, which keeps the "(copy)" suffix English because "a file's name does not change with the window's language" (`docs/adr/054-a-name-already-taken.md:39-44`). Skwir's layout rules already help: rows choose their variant by measurement in prepaint, and cut text gets a tooltip, so longer translations mostly fit. Fixed widths such as History's 420 px, the outline's 220 px and the board and columns' 240 px will truncate more often.

## Fluent fits Skwir's engineering; gettext fits its translators

The options fall into six families, and Skwir's rules sort them quickly. The table judges each against what Skwir needs:

- plurals and noun kinds chosen by translators, not by Rust `match`es;
- checks at compile time;
- catalogs that load at run time, for plugins from outside;
- builds for every system made from Linux;
- a memory model the idle budget can afford.

| Option | Plurals and noun kinds | Checked at compile time | Loads at run time | Every system | Memory at run time | Translator tooling | State, Nov 2026 |
|---|---|---|---|---|---|---|---|
| **Fluent FTL** (fluent-bundle + a checked macro) | Selectors chosen per language; plural data at CLDR 37 | Ids and argument names against English (`fl!`); every locale (fluent-typed) | Yes, from bytes | Pure Rust, Apache-2.0 or MIT | Source text, syntax tree and id map per loaded locale (unmeasured) | Weblate and Crowdin show selectors as raw FTL; Pontoon has a structured editor | fluent-bundle 0.16.0 (May 2025), maintenance only |
| **gettext PO** through gettext-rs | By count only; noun kinds as separate messages | No (strings are extracted) | Yes (`.mo`) | libintl on Linux; elsewhere GNU gettext built from source with autotools, statically linked under LGPL | Memory-mapped `.mo`, the lightest | Native everywhere, fuzzy state, offline editors | 0.8.0 (Aug 2026); `setlocale` unsafe, process-wide |
| **gettext PO**, pure-Rust loader | Same | No | Yes | Pure Rust | Heap copy, or Skwir's own tables | Same | `gettext` 0.4.0 (2019) dormant, so Skwir writes the loader |
| **rust-i18n** YAML | None | No; a missing key shows `locale.key` | With the `load-path` feature | Pure Rust, MIT | Map built at first use; 15 to 40 ns per lookup | Per-locale YAML only, no plural model | 4.2.4 (Sep 2026), very active |
| **Generated code** (fluent-static, typed-i18n, `match` arms) | Varies | Strongest | No | Pure Rust | No parsing | None; rebuild per translation | Single maintainers |
| **MessageFormat 2** | Full | — | — | — | — | Some platforms | ICU4X parser unreleased (2026-11-11) |

Sources: [fluent-bundle](https://crates.io/crates/fluent-bundle), [intl_pluralrules](https://crates.io/crates/intl_pluralrules), [i18n-embed-fl](https://github.com/kellpossible/cargo-i18n/blob/master/i18n-embed-fl/src/lib.rs), [fluent-typed](https://github.com/akesson/fluent-typed), [gettext-sys README](https://github.com/gettext-rs/gettext-rs/blob/master/gettext-sys/README.md), [gettext](https://crates.io/crates/gettext), [rust-i18n](https://github.com/longbridge/rust-i18n), [rust-i18n PR #150](https://github.com/longbridge/rust-i18n/pull/150), [fluent-static](https://github.com/zaytsev/fluent-static), [Weblate Fluent format](https://docs.weblate.org/en/latest/formats/fluent.html), [ICU4X messageformat](https://github.com/unicode-org/icu4x/tree/main/components/experimental/src/messageformat).

**Fluent is the recommended format.** It keys messages by id rather than by their English text, and gives translators named arguments they can reorder. Each language can add plural, gender or case variants without the English or other languages changing, which Mozilla calls asymmetric localisation ([Mozilla Hacks: Fluent 1.0](https://hacks.mozilla.org/2019/04/fluent-1-0-a-localization-system-for-natural-sounding-translations/)). These are the reasons fish gave when it moved its Rust messages from gettext to Fluent in 4.8.0, released 2026-06-24 ([fish commit 8816960b](https://github.com/fish-shell/fish-shell/commit/8816960b871cc75fa6f448ce3483a2b9dc4b0c81), [fish CHANGELOG](https://github.com/fish-shell/fish-shell/blob/master/CHANGELOG.rst)).

COSMIC is the closest analogue to Skwir: Rust, a GPU toolkit of its own, and dozens of crates. It runs the same stack: one FTL file per crate per language through i18n-embed and its `fl!` macro, with an ICU4X numeric collator and jiff-icu for the locale work around the messages ([cosmic-files Cargo.toml](https://github.com/pop-os/cosmic-files/blob/master/Cargo.toml), [cosmic-files localize.rs](https://github.com/pop-os/cosmic-files/blob/master/src/localize.rs)). Fluent's author told Zed's localisation RFC "I recommend going with Fluent now", because a lossless converter to MessageFormat 2 is being validated ([Zed discussion #43592](https://github.com/zed-industries/zed/discussions/43592)). On Skwir's own terms, Fluent is pure Rust under Apache-2.0 or MIT, every Fluent front end surveyed supports one catalog per crate, and FTL loads from bytes at run time, which plugins from outside need.

Fluent's weaknesses are real, but mostly sit where Skwir would not use it:

- **Slow maintenance.** fluent-bundle was last released on 2025-05-22, with only maintenance commits since ([fluent-bundle CHANGELOG](https://github.com/projectfluent/fluent-rs/blob/main/fluent-bundle/CHANGELOG.md)).
- **Old plural data.** Its plural rules come from intl_pluralrules 7.0.2, last released in 2022, at **CLDR 37**, while ICU4X is at CLDR 49 ([pluralrules source](https://github.com/zbraniecki/pluralrules)).
- **No locale formatting.** `NUMBER()` selects plurals but formats with `f64::to_string()`, so it writes no locale separators, and `DATETIME()` is still a `TODO` ([number.rs](https://github.com/projectfluent/fluent-rs/blob/main/fluent-bundle/src/types/number.rs), [bundle.rs](https://github.com/projectfluent/fluent-rs/blob/main/fluent-bundle/src/bundle.rs)). The request to port numbers to ICU4X has been open since 2022 ([fluent-rs#269](https://github.com/projectfluent/fluent-rs/issues/269)).

Skwir would format every number, size and date itself before it enters a message, as COSMIC does, which leaves only the plural data exposed.

The heavier cost lands on translators. Weblate's Fluent support lists plurals as unsupported and shows selectors as raw FTL. Crowdin's FTL support has no pluralisation. Only Mozilla's Pontoon offers an editor structured for Fluent, with a field per plural category ([Weblate Fluent format](https://docs.weblate.org/en/latest/formats/fluent.html), [Crowdin FTL](https://store.crowdin.com/ftl), [Pontoon's Fluent editor](https://blog.mozilla.org/l10n/2019/04/11/implementing-fluent-in-a-localization-tool/)). Fluent also has no "fuzzy" state for translations that need review, so fish is building a "needs-review" marking of its own ([fish#11940](https://github.com/fish-shell/fish-shell/issues/11940)). Veloren found that Weblate handles Fluent terms badly ([Veloren#1582](https://gitlab.com/veloren/veloren/-/issues/1582)).

**gettext PO is the credible runner-up.** It is the right choice only if translator familiarity outweighs Skwir's build and boundary constraints. PO is the common language of volunteer translators and offline editors. Every platform edits its plural forms one by one, keeps a fuzzy state and merges templates ([Weblate add-ons](https://docs.weblate.org/en/latest/admin/addons.html)).

Its drawbacks fall on Skwir's builds and boundaries:

- **C and LGPL builds.** The maintained binding, gettext-rs 0.8.0, links GNU libintl. Where the system has none, it builds GNU gettext 1.0 from source with autotools and links it statically, so "you have to abide by LGPL" ([gettext-sys README](https://github.com/gettext-rs/gettext-rs/blob/master/gettext-sys/README.md)). Its CI tests Windows only through MSYS2, and its `setlocale` became `unsafe` because it is not thread-safe ([gettext-rs CHANGELOG](https://github.com/gettext-rs/gettext-rs/blob/master/gettext-rs/CHANGELOG.md)). That conflicts with Skwir's Windows and macOS packages, which are made on Linux (ADR-074, ADR-075), and with switching language inside a process that runs many threads.
- **No maintained pure-Rust loader.** The pure-Rust `gettext` crate was last released in 2019 and copies the whole catalog into a `HashMap` ([justinas/gettext](https://github.com/justinas/gettext)). The workable gettext route is PO as a format with Skwir owning the loader. Slint's bundling is the reference design: it compiles `.po` files into indexed tables per language at build time ([Slint translations.rs](https://github.com/slint-ui/slint/blob/master/internal/compiler/translations.rs)). Slint itself is GPL or proprietary, so it is a model to copy, not a dependency.
- **English as the key.** PO keys messages by their English text, so a typo fix invalidates every translation, which was one of fish's complaints ([fish#11400](https://github.com/fish-shell/fish-shell/issues/11400)). It also expresses noun kinds only as separate messages.

The rest fall short:

- **rust-i18n.** Version 4.2.4 is very active and is what gpui-component uses, but it has no plurals (the request has been open since 2023) and no checks at compile time. A missing key shows as `"locale.key"` at run time ([rust-i18n#65](https://github.com/longbridge/rust-i18n/issues/65), [rust-i18n macro source](https://github.com/longbridge/rust-i18n/blob/main/crates/macro/src/lib.rs)). gpui-component's own guide lists what it leaves to the application: plurals, number and date formatting, and RTL ([gpui-component i18n.md](https://github.com/longbridge/gpui-component/blob/main/website/docs/i18n.md)).
- **Generated code.** Generating Rust from catalogs, as fluent-static, typed-i18n or Sniffnet's `match` arms do, gives the strongest checks. But it cannot load a catalog the build never saw, which rules out plugins from outside ([fluent-static](https://github.com/zaytsev/fluent-static)).
- **MessageFormat 2.** It became a stable specification in CLDR 47 on 2025-03-13 ([Unicode blog](https://blog.unicode.org/2025/03/unicode-cldr-47-release-messageformat-2.html)). ICU4X has only an unreleased parser for simple messages, committed 2026-11-11, and its implementation epic has no assignee ([icu4x#3028](https://github.com/unicode-org/icu4x/issues/3028)). It is a migration target reachable from Fluent, not a choice for 2026.

The ready-made Fluent front ends resolve messages too early. `fl!` checks message ids, attributes and argument names against the English FTL at compile time ([i18n-embed-fl](https://github.com/kellpossible/cargo-i18n/blob/master/i18n-embed-fl/src/lib.rs)). fluent-typed goes further: it checks every locale, types the arguments and warns about unused messages ([fluent-typed](https://github.com/akesson/fluent-typed)). Both return a `String` at the call site, which is exactly the finished text that must not cross Skwir's boundaries.

**Skwir needs a thin layer of its own.** It is a macro that builds a message value, checked at compile time and resolved later, over fluent-bundle as the runtime. fish's `localize!` is the model: it keeps the English beside the id in the source and generates `en.ftl` from it ([fish commit 8816960b](https://github.com/fish-shell/fish-shell/commit/8816960b871cc75fa6f448ce3483a2b9dc4b0c81)). New contributors revived i18n-embed's `fl!` between September and November 2026 ([cargo-i18n commits](https://github.com/kellpossible/cargo-i18n/commits/master)), so it is the fallback if the in-house macro proves too costly.

## A typed message that core owns and every crate fills

The design rests on one type, here called `Text`. It holds a domain (the crate's or plugin's id), a message id and typed arguments. Its other form is a literal, for text Skwir did not write: an agent's plan title, an OS message, a plugin from outside on protocol 1. `Text` belongs in `skwir-core` under the small-core rule, because every plugin and the shell must agree on how text resolves. It derives `Serialize` and `JsonSchema`, so it travels wherever English travels today: in `CommandSpec`, `SettingSpec`, `MenuItem`, plan titles, `Words` and the plugin protocol.

Once the registration functions take `Text` instead of `&str`, a stray English literal no longer compiles, so the type system becomes the check AGENTS.md asks for. An escape hatch, `Text::literal`, would be allowed only under a clippy `disallowed-methods` exception with a reason, as Skwir already requires for allowances in code. What the types cannot reach, such as the 31 `.child("Literal")` and 25 `.child(format!(…))` calls in `crates/ui`, a pseudo-locale run catches.

Typed arguments give today's scattered conventions one place each:

- **`Name`** draws the locale's quotation marks (French « », German „ “) where 673 sites now write English quotes. It is also the one place to isolate a right-to-left name from the sentence around it, and to neutralise bidi override characters in the name.
- **`Count`** carries the plural.
- **`Kind`** (folder, file, link) lets translators make gender agree. Dolphin does the same with separate strings per kind and a translatable combining pattern, `"%1, %2 (%3)"` ([dolphinview.cpp](https://invent.kde.org/system/dolphin/-/blob/master/src/views/dolphinview.cpp)).
- **`Size` and `Instant`** are formatted by ICU4X before they reach Fluent.

Redaction, which the commands invariant now applies to rendered strings, can then act on the arguments before rendering. That is sturdier in any language.

Catalogs follow plugin independence. Each crate ships `l10n/<lang>/<crate>.ftl`. A plugin registers its catalog with its other contributions, tagged with its id and withdrawn on disable, and `crates/skwir/tests/plugins_toggle.rs` gains that kind of contribution. Words that two plugins must share become core-owned ids: the "Compress", "Open With" and "Tags" submenus, and the settings sections. That fixes the English joins whether or not anything is translated. A setting's title, description and short first sentence become one message with attributes. This replaces `settings::first_sentence`, which splits at `". "` and would never split a Japanese description at "。" (`crates/ui/src/settings.rs:1988-1998`).

Messages are resolved where they are drawn, as the theme's fonts already are. The shell keeps the `Theme` as a gpui `Global`, resolves it again when a summed revision changes, and lets each element read it where it draws, never copying it (`crates/ui/src/theme.rs:380`, `crates/ui/src/shell.rs:3349-3385`, ADR-073). The active catalogs can follow the same model: core holds the language, and a locale revision joins `theme_inputs_of`. Messages without arguments are resolved once per revision. Messages with arguments are resolved at each draw, and Skwir draws only when something asks for a frame, not at every display refresh.

Switching language then means parsing the new catalog on a worker, swapping it in and refreshing the windows. gpui-component, whose locale lives outside gpui's change tracking, has to rebuild its cached menus by hand instead ([gpui-component i18n.md](https://github.com/longbridge/gpui-component/blob/main/website/docs/i18n.md)). Some system text would still change only at the next start: cosmic-text reads its fallback locale once per process ([cosmic-text system.rs](https://docs.rs/crate/cosmic-text/0.19.0/source/src/font/system.rs)), and macOS chooses a bundle's language at launch. So the language setting can switch Skwir's own text live from the start, or begin as a setting that waits for a restart, which the settings layer already supports.

**Agents should read English by default, and the user should never have to.** A command's id is its contract. MCP clients cache tool lists, so a description that changed with the window's language would change an agent's prompt underneath it. Models also read English instructions well, and they can still answer the user in French. The proposal follows from that:

- MCP tool titles and descriptions, and the CLI's help, are resolved in the source language.
- Display text inside JSON results, such as a facet's "1 file", is resolved in the agent's language: English unless the control plugin is told otherwise.
- Everything the user reads in the window is resolved in the user's language from the same `Text`: the permission question, the plan review, toasts, plans written by agents included.
- An agent's own words, such as the titles it composes, stay literals and are shown as written.

The palette can keep matching a command's id beside its translated title, so English muscle memory still works. The opposing view, that one surface means one language, carries weight for users who drive Skwir entirely through agents in their own language. A setting in the control plugin answers them without changing the default.

Plugins from outside need protocol version 2:

- `InitializeParams` gains the negotiated language list.
- The manifest's titles become ids into FTL files shipped beside `plugin.toml`. That is a breaking change under `deny_unknown_fields`, hence the new version.
- Answers such as `Inspection.title`, `CommandAnswer::Text` and plan titles can carry `{id, args}`, which the host resolves with the plugin's own catalog. A WebAssembly module then needs no Fluent runtime of its own.
- Plain strings from protocol-1 plugins keep working as literals.

That matches the consensus in Zed's RFC, where Fluent's author said that plugins supplying their own string tables "matches what generally plugin-enabled apps do" ([Zed discussion #43592](https://github.com/zed-industries/zed/discussions/43592)).

The budgets constrain how catalogs load. Idle memory is budgeted at 100 MiB of Skwir's own share, last measured at **83.2 MiB** (`docs/STATUS-LOG.md`, 2026-11-09). The live heap is about 20 MiB, of which the MIME database takes 1.0 MiB and the exclusions' tables 0.8 MiB. ADR-128 found that each MiB of code added costs 0.73 MiB of idle memory unless it is laid out in start order, and every function a start runs must be listed in `tools/build/startup-order.txt`.

A `FluentResource` keeps its source text and a syntax tree that points into it, and the bundle copies every message id into a hash map ([resource.rs](https://github.com/projectfluent/fluent-rs/blob/main/fluent-bundle/src/resource.rs)). A locale of several thousand messages plausibly costs about a megabyte of heap. That is an estimate, not a measurement. A user of another language would hold two bundles: their own, and English for messages their language lacks.

The plan that fits Skwir's start sequence is to embed each language's FTL as read-only data, where only the pages actually read become resident. The active language is parsed on a worker beside `fonts::read_ahead`, which the first theme already waits for (`crates/ui/src/fonts.rs:185-191`). Declaring commands and settings needs no catalog, because the registries hold ids. If `just idle-pss` or the first frame shows a cost, the next step is to compile catalogs at build time into indexed static tables, as Slint does. That trades parse time and heap for code Skwir would own. The only published lookup timings are rust-i18n's, 15 to 40 ns per key ([rust-i18n PR #150](https://github.com/longbridge/rust-i18n/pull/150)). fluent-bundle has benchmarks in its repository but no published results.

## Dates, sizes and name order belong to ICU4X and the system

Messages carry words. Everything around the words is locale data, which ICU4X provides and the operating system adjusts. ICU4X 2.4.0 (2026-10-22, CLDR 49) is pure Rust under the Unicode-3.0 licence. Its collator, datetime, decimal, plurals and list components are stable, while relative time, units and duration stay in `icu_experimental` 0.7 ([ICU4X CHANGELOG](https://github.com/unicode-org/icu4x/blob/main/CHANGELOG.md)). Its normaliser, properties and locale crates are **already in Skwir's `Cargo.lock` at 2.4.0**, through `idna_adapter` and parley.

A bench built for this research measured what each component adds to a binary: **the collator 1.21 MiB, datetime 1.13 MiB, decimal 60 KiB, plurals 59 KiB, relative time 118 KiB**. The bench (ICU4X 2.4, glibc 2.44, Rust 1.99.1, x86_64) was not kept. It used stripped builds with fat LTO and compiled data for all CLDR locales, on a loaded machine, so expect ±40 % on timings. ICU4X's data generator can cut a one-locale data file from 5 MB to 19 KB by keeping only what a binary uses ([ICU4X data management](https://github.com/unicode-org/icu4x/blob/main/tutorials/data-management.md)). A subset of locales was not measured.

Locale detection needs its own seam, `skwir_platform::locale`, beside `xdg`, `calendar` and `mime`, because messages, formats and collation are separate categories on every system.

- **Linux.** gettext's rules apply ([GNU gettext manual](https://www.gnu.org/software/gettext/manual/html_node/The-LANGUAGE-variable.html), [locale variables](https://www.gnu.org/software/gettext/manual/html_node/Locale-Environment-Variables.html)):
  - for messages, `LANGUAGE` comes first, but is ignored under the C locale;
  - then come `LC_ALL`, the category's own `LC_*` and `LANG`;
  - variables set to an empty value are skipped.

  `C`, `C.UTF-8` and `POSIX` mean "no localisation", and modifiers need a real mapping: `sr_RS@latin` is `sr-Latn-RS`.
- **sys-locale** is already compiled in through cosmic-text. It returns only the messages list, does not apply the C rule and maps modifiers crudely ([sys-locale](https://github.com/1Password/sys-locale)), so it can supply the macOS and Windows calls but not the Linux rules.
- **macOS and Windows.** macOS separates preferred languages from region settings. Windows separates the display-language list, which holds only installed languages, from the user locale used for formats ([NSLocale.preferredLanguages](https://developer.apple.com/documentation/foundation/nslocale/preferredlanguages), [GetUserPreferredUILanguages](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-getuserpreferreduilanguages)). A Windows user cannot pick a display language they have not installed, so Skwir needs a language setting of its own, "Automatic" by default with an override.
- **Negotiation.** ICU4X has fallback between locales but no negotiation; its LocaleMatcher has been open since 2023 ([icu4x#3023](https://github.com/unicode-org/icu4x/issues/3023)). Matching the user's languages against the shipped catalogs therefore uses fluent-langneg ([fluent-langneg](https://crates.io/crates/fluent-langneg)).

The existing readers then use the same seam: desktop entries, paper size, and the first weekday, which `calendar::prewarm` already reads on a worker.

Dates need ICU4X, because jiff's strftime "does not currently support any form of localization" and points to ICU4X through jiff-icu ([jiff strtime](https://docs.rs/crate/jiff/0.2.39/source/src/fmt/strtime/mod.rs)). `friendly_time`'s "Today 14:02" and "Tuesday 09:30" become whole messages, with times and weekdays formatted by ICU4X. The timeline's English month tables go, and day boundaries stay those of `skwir_platform::calendar` (ADR-017).

The user's format overrides need the system. Firefox takes Windows' `LOCALE_SSHORTDATE` patterns, and on GTK it takes `LC_TIME` plus GNOME's `clock-format` hour cycle, applied over ICU data ([OSPreferences_gtk.cpp](https://github.com/mozilla-firefox/firefox/blob/main/intl/locale/gtk/OSPreferences_gtk.cpp), [OSPreferences_win.cpp](https://github.com/mozilla-firefox/firefox/blob/main/intl/locale/windows/OSPreferences_win.cpp)). On Windows, `GetLocaleInfoEx` returns the user's custom formats by default ([GetLocaleInfoEx](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-getlocaleinfoex)). ICU4X accepts the hour cycle and first weekday as `-u-hc` and `-u-fw` locale extensions, but not arbitrary patterns. It also does not reproduce the Linux habit of setting `LC_TIME=en_DK` to get ISO dates: in the bench, `en-DK` gave "12 Nov 2026, 16.09" where glibc gives 2026-11-12. So the ISO choice in `ui.date_format` stays.

Two ICU4X defaults need decisions: Persian (`fa`) formats dates in the Persian calendar, and Arabic dates carry U+200F direction marks. ICU4X's own bridge to the OS, `icu_host_info`, is unpublished and supports neither date nor number formats on any system ([icu_host_info](https://github.com/unicode-org/icu4x/tree/main/utils/host_info)).

Numbers and sizes pass through a few helpers: `size_said`, `thousands`, `count`, the percent, `short_count`, `speed`, `took` and `time_left`. So the conversion is concentrated. icu_decimal writes French `123 456,7` with U+202F as the group separator, which gpui's line wrapper already treats as a non-breaking character (the bench; `vendor/zed/crates/gpui/src/text_system/line_wrapper.rs:641-681`).

Sizes need a decision before any translation. Skwir uses three conventions today:

- it divides by 1024 but labels the result `KB` (`crates/core/src/fs/mod.rs:23-38`);
- it labels volumes in powers of ten, "to match the number on the label" (`crates/plugins/places/src/lib.rs:227-237`);
- it writes `MiB` in limit messages.

GNOME defaults to 1000-based kB, and KDE to 1024-based KiB ([glib gutils.c](https://github.com/GNOME/glib/blob/main/glib/gutils.c), [KDE kformatprivate.cpp](https://github.com/KDE/kcoreaddons/blob/master/src/lib/util/kformatprivate.cpp)). **CLDR has no kibibyte units at all**, only SI ones such as French `ko`, `Mo` and `Go` ([CLDR units](https://github.com/unicode-org/cldr-json/tree/main/cldr-json/cldr-units-full/main)). So if Skwir stays 1024-based, its unit names stay messages whose translation translators choose ("Ko", "Kio"), with the number formatted by icu_decimal. COSMIC left exactly this as an English `TODO` ([cosmic-files lib.rs](https://github.com/pop-os/cosmic-files/blob/master/src/lib.rs)). Lists joined with `", "` and `" and "` become icu_list or messages. Durations and "time left" become messages around numbers formatted by ICU4X.

Name order is the one place where locale correctness costs real time, and it is independent of translation. `collate::sort_key` is deliberately not a locale's collation:

- it lowercases names;
- it drops Latin accents using a table that covers U+00C0 to U+017F;
- it folds decomposed (NFD) names to match composed ones;
- it orders runs of digits by value, and breaks ties by bytes.

Each listing caches the key per entry (`crates/core/src/collate.rs:1-95`, `crates/core/src/location.rs:325`), which is what the Scale rule needs at 100,000 entries. It misorders Swedish, Danish and German phonebook order, and gives Greek, Cyrillic and CJK only code-point order.

On 100,000 synthetic names, the bench found ICU4X's numeric collator **too slow to compare directly**, at 0.6 to 1.2 s per single-threaded sort. Through its sort keys it is fast: the keys are 1.4 times the names' bytes and take about 105 to 120 ms to generate, or 127 to 147 ms including the sort. The keys gave the same order as direct comparison at every position. The OS collators match Finder or Explorer, but they are documented to change between releases and need one call per name ([CompareStringEx](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-comparestringex), [localizedStandardCompare](https://developer.apple.com/documentation/foundation/nsstring/localizedstandardcompare(_:))). glibc's `strcoll` has no numeric mode. In the bench it ignored punctuation and put Hangul names before Latin ones, and its keys were seven times the names' size.

The recommendation is ICU4X keys behind the existing key seam:

- generated on workers, as folders already are (ADR-120, ADR-121);
- held in memory only, because ICU4X 2.4 changed the key format;
- with today's folding kept for the "no localisation" case.

The comparison that matters is unmeasured. The bench raced ICU4X against its own simple comparator, not against Skwir's cached keys, and how much the order an English user sees today would change is unknown. Type-to-find shares the same folding (`collate::Prefix`), and how to keep prefix matching consistent with a collator-based order was not worked out.

Separately, search terms are matched with `to_lowercase().contains`. So `ecole` finds `École` in type-to-find but not in a search, an inconsistency that exists today.

The environment can supply more than it does now:

- **Linux type names.** `comment_of` could take the `<comment xml:lang>` that matches the user's language from the system's own files: a translated type name at no data cost.
- **User folders on Windows and macOS.** Skwir shows their English on-disk names where Finder shows "Bilder" for Pictures in German ([Apple: Display Names](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPFileSystem/Articles/DisplayNames.html)). `SHGetLocalizedName` and `FileManager.displayName(atPath:)` give the shown names ([displayName(atPath:)](https://developer.apple.com/documentation/foundation/filemanager/displayname(atpath:))), once it is decided whether the trail shows the display name or the real name.
- **Place titles** ("Home", "Trash", "Recent", "Nearby") become messages; on Windows the trash is the Recycle Bin.
- **Key caps** such as "Ctrl", "Esc" and "Page Up" become messages, while bindings stay in gpui notation. This is Qt's split between a portable form that is stored and a native, translated form that is shown ([QKeySequence](https://doc.qt.io/qt-6/qkeysequence.html)).

The query language must not be translated. Windows Search found that keywords localised to the interface language break queries written in another, so it added canonical names it tells developers to always use ([Microsoft: Advanced Query Syntax](https://learn.microsoft.com/en-us/windows/win32/search/-search-3x-advancedquerysyntax)). Skwir's `name:`, `kind:`, `modified>=`, `today` and `this-week` stay the canonical stored form of saved searches and places (ADR-109). Pills, chips and completions show translated labels, which `facets.rs` already pairs with the query text (`crates/plugins/query/src/facets.rs:41-63`). The reader of plain words in `assist.rs` keeps its English vocabulary until a language brings its own.

## Scripts, packaging and translators bound the first release

### gpui cannot mirror a layout, so the first languages read left to right

Right-to-left support has three levels, and only the middle one is within Skwir's reach.

**Level 1, shaping and visual order within a line,** is gpui's job, and it works only partly. Single lines are shaped correctly on Linux (cosmic-text with harfrust) and on macOS (CoreText). But a wrapped right-to-left line draws its rows in the wrong order on macOS, and on Windows `DrawGlyphRun` ignores `bidiLevel`, so right-to-left runs draw backwards until an open upstream fix lands ([zed#31102](https://github.com/zed-industries/zed/issues/31102), [DWRITE_GLYPH_RUN](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/ns-dwrite-dwrite_glyph_run)). gpui's caret mapping assumes that byte index and x position rise together, so carets, selections and IME rectangles in right-to-left text are wrong on every system ([gpui-bidi](https://docs.rs/gpui-bidi)).

**Level 2, isolating each file name from its sentence and neutralising its override characters,** is worth doing now. Dolphin still displays `Hello_`, U+202E (right-to-left override), `gnp.js` as `Hello_sj.png`, a bug open since 2010 ([KDE bug 260677](https://bugs.kde.org/show_bug.cgi?id=260677)), and security tooling flags exactly that spoof ([Elastic rule](https://www.elastic.co/guide/en/security/current/prebuilt-rule-8-19-21-file-with-right-to-left-override-character-rtlo-created-executed.html)). Skwir handles neither today: no code for it was found in the UI (read, not tried in a window).

**Level 3, a mirrored window, is a separate project:**

- gpui's `Style` has no direction field and always hands taffy a left-to-right layout, although taffy 0.15 supports `Direction::Rtl` (`vendor/zed/crates/gpui/src/taffy.rs:451-529`, [taffy style](https://docs.rs/crate/taffy/0.15.0/source/src/style/mod.rs)).
- Skwir lays out with 168 physical-side paddings and elements it places by hand in prepaint.
- Upstream closed a 1,500-line bidi pull request as "very very risky" ([zed#57172](https://github.com/zed-industries/zed/pull/57172)).
- No Rust toolkit mirrors layouts; Slint, egui, iced and COSMIC all have the request open ([slint#2294](https://github.com/slint-ui/slint/issues/2294), [egui#1016](https://github.com/emilk/egui/issues/1016), [iced#250](https://github.com/iced-rs/iced/issues/250), [cosmic-epoch#888](https://github.com/pop-os/cosmic-epoch/issues/888)).

The ADR should say plainly that Arabic, Hebrew and Persian interfaces wait for that track.

By default, Fluent wraps every argument in the invisible isolation marks U+2068 and U+2069 ([bundle.rs](https://github.com/projectfluent/fluent-rs/blob/main/fluent-bundle/src/bundle.rs)). On Linux, harfrust classes them as default-ignorable and hides them ([harfrust ot_shape.rs](https://docs.rs/crate/harfrust/0.5.2/source/src/hb/ot_shape.rs)); on macOS and Windows this is unverified. Veloren had to turn the marks off because its toolkits drew them. COSMIC keeps them on in production and turns them off only in tests ([Veloren#1649](https://gitlab.com/veloren/veloren/-/issues/1649), [cosmic-settings localize.rs](https://github.com/pop-os/cosmic-settings/blob/master/cosmic-settings/src/localize.rs)). In Skwir the marks must never reach the CLI, MCP, the clipboard or tests. The simplest rule is to turn off Fluent's isolation of every argument, and let the `Name` argument isolate user data only where the window draws it. That choice should be revisited once a right-to-left interface becomes possible.

Fonts and input set the remaining limits:

- **Fonts.** Skwir's own Inter and JetBrains Mono cover Latin, Greek and Cyrillic only (checked with `fc-query` on the built files), so CJK, Indic and other scripts draw in system fallback fonts. Bundling Noto Sans CJK would add about 19 MB per weight ([noto-cjk](https://github.com/notofonts/noto-cjk/tree/main/Sans/OTC)), against "harness the environment".
- **CJK fallback on Linux.** cosmic-text picks CJK fallback fonts from a hard-coded Noto list, keyed by an exact locale string such as `ja` or `zh-TW`, while sys-locale reports `ja-JP` ([cosmic-text fallback](https://github.com/pop-os/cosmic-text/blob/main/src/font/fallback/unix.rs)). A Japanese desktop therefore likely gets Simplified Chinese glyph forms. This is inferred from both sources, not observed.
- **Line wrapping.** gpui's wrapper uses a hand-written list of word characters that leaves out Greek, Armenian, Georgian, Devanagari and Thai (`line_wrapper.rs:641-681`).
- **Missing glyphs.** gpui has an `on_missing_glyphs` hook that Skwir does not use; it could warn when the chosen language lacks fonts.

These are candidates for gpui patches if the first, left-to-right languages include Greek or CJK.

IME works on Wayland, X11, Windows and macOS, with open bugs worth tracking when gpui is vendored again: XIM never reconnects after an error, and it duplicates Japanese preedit text ([zed#60578](https://github.com/zed-industries/zed/issues/60578), [zed#66087](https://github.com/zed-industries/zed/issues/66087)).

Screen readers will hear the translated `aria_label` names. They stay cheap, because they are built only while a reader listens. But gpui never sets AccessKit's per-node `language`, and AccessKit's AT-SPI adapter returns an empty locale ([accesskit_unix accessible.rs](https://docs.rs/crate/accesskit_unix/0.22.1/source/src/atspi/interfaces/accessible.rs)). Until a gpui patch sets the window's language, readers choose a voice by guesswork.

### Embed the catalogs, translate metadata through gettext, use Weblate

Catalogs that live in Skwir's repository belong inside the binary. Data found under `share/skwir/`, like the fonts, needs entries in every package and its check: the deb and rpm asset lists, the AppImage, Nix, three AUR packages, and the macOS and Windows scripts (AGENTS.md, ADR-118). Catalogs embedded with `include_bytes!` per language, as the toolbar icons are, need none of that, and the pages of unused languages stay out of memory. The binary grows by each language's FTL, which was not measured. Plugins from outside carry their catalogs in their own package.

Freedesktop metadata goes through gettext, whatever the interface uses:

- **Desktop and AppStream files** are translated by extracting their strings into a PO template and merging the translations back with `msgfmt --desktop` or `--xml`, or with itstool ([AppStream translation guide](https://www.freedesktop.org/software/appstream/docs/sect-Quickstart-Translation.html)). Since version 2026.10, Hosted Weblate's xgettext add-on extracts both, with ITS rules bundled ([Weblate add-ons](https://docs.weblate.org/en/latest/admin/addons.html)). COSMIC's `.desktop` files sit outside Weblate for want of exactly this ([cosmic-epoch#2263](https://github.com/pop-os/cosmic-epoch/issues/2263)).
- **AppStream's `<translation>` tag** knows only the `gettext` and `qt` types, so software centres cannot list the interface languages of a Fluent application ([AppStream metadata](https://www.freedesktop.org/software/appstream/docs/chap-Metadata.html)).

On macOS, the bundle Skwir writes declares no localisations. Toolkits outside Cocoa found that such an application is greyed out in the per-app language list, and gets English system menus, until it ships `CFBundleLocalizations` and one `.lproj` folder per language ([KDE bug 454677](https://bugs.kde.org/show_bug.cgi?id=454677), [OpenTodoList MR !297](https://gitlab.com/rpdev/opentodolist/-/merge_requests/297), [CFBundleLocalizations](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundlelocalizations)). `tools/package/macos.sh` can generate both from the list of catalogs, and Skwir should read the language macOS resolved for the bundle. The vendored gpui recognises the Window menu by the literal title `"Window"` (`vendor/zed/crates/gpui_macos/src/platform.rs`). Before Skwir passes translated menus, that wants a patch that marks the menu with a flag instead. The Windows MSI, made by wixl, has no localisation options and shows no dialogs, so it stays in English.

For translators, Hosted Weblate is the one platform that takes all of Skwir's formats: FTL, the metadata's PO, the guide's Markdown and WiX files. Its Libre plan is free for public projects ([Weblate hosting](https://weblate.org/en/hosting/)).

The Libre plan carries the 160k plan's limit, counted as source strings times the number of languages plus one. With 6,000 to 8,000 source strings before duplicates are removed, it fits **roughly 20 to 25 languages**. That is an inference from the stated formula. It is about as many languages as a project of Skwir's size can expect to keep maintained (10 to 30): COSMIC, with a company and a desktop behind it, has 24 of its 77 languages at 95 % or more ([Weblate API statistics](https://hosted.weblate.org/api/projects/pop-os/statistics/), [Weblate API languages](https://hosted.weblate.org/api/projects/pop-os/languages/)). Keeping the workers' internal error phrases in English, and leaving the exclusions' 539 descriptions for later, keeps the count down.

Fluent's editing burden calls for some discipline:

- simple English messages;
- a translator comment on every message with arguments;
- a glossary of Skwir's own terms (entry, place, shelf, lens, plan);
- no Fluent terms;
- ids that change only when the meaning changes, since renaming an id deletes its translations on Weblate ([Veloren developer's guide](https://book.veloren.net/contributors/translators/developers-guide.html)).

Weblate's GitHub App can squash each language's work into one pull request, with a `Co-authored-by` trailer for every translator ([Weblate add-ons](https://docs.weblate.org/en/latest/admin/addons.html)).

Process completes the workflow. CI should:

- parse every catalog;
- compare each catalog's ids and variables with the English;
- extend `keymap_titles.rs`'s rule that no two titles read alike to every language;
- run a pseudo-locale (fluent-pseudo through `set_transform`, as Firefox does, accented and elongated) in the real-window checks and the screenshots, to catch truncation and text that was never converted ([Bug 1450781](https://bugzilla.mozilla.org/show_bug.cgi?id=1450781)).

Tests assert message ids, or English with isolation off, and the settings wording test applies to English only. A language ships once it passes a published completeness threshold (F-Droid uses 70 %, [F-Droid](https://f-droid.org/docs/Translation_and_Localization/)), after a string freeze announced before the release.

Machine and model drafts enter Weblate only as suggestions, or as strings marked "needing edit", never as approved translations ([Weblate machine translation](https://docs.weblate.org/en/latest/admin/machine.html)). That mirrors Skwir's own ADR-000 rule that AI output is a suggestion until a human confirms it. The translation guide should say that only Skwir's strings, never user data, go to those services. Several GNOME projects forbid such contributions outright ([GNOME Discourse](https://discourse.gnome.org/t/translations-with-ai/34668)).

## What is unmeasured, and the first seven steps

No option has been measured in Skwir. These are unknown:

- the heap and parse time of a catalog of several thousand messages, against the 100 MiB own share and the first frame's 50 ms share;
- the cost per draw of resolving messages with arguments (the status footer resolves its text in `render`);
- the binary growth per embedded language;
- whether CoreText and DirectWrite draw U+2068 and U+2069 invisibly;
- ICU4X keys against Skwir's current `sort_key` on `bench-data/flat100k`, and how far the order would move;
- datetime's size for a subset of locales;
- which of Skwir's target languages have plural rules that changed between CLDR 37 and 49;
- how Weblate's editor really presents a Fluent selector;
- the compile time of a proc macro across about fifty crates;
- whether GNOME's and KDE's region settings reach `LC_TIME`;
- right-to-left text, CJK and IME in a real Skwir window, never tried.

The string counts are occurrences found by a lexer, not de-duplicated messages, and every timing here comes from one loaded machine.

## Conclusion

Internationalisation turns out to be the third use of a pattern Skwir already trusts. Commands became serialisable data so that the keymap, scripts and agents share one surface. Fonts became roles read where they are drawn so that a change shows at once. Messages as typed data are the same move applied to words. Once the words are data, the engine behind them becomes replaceable: Fluent today, MessageFormat 2 through its converter when ICU4X ships an engine. Live language switching becomes close to free, and agents and the user can each read the language that suits them without a second command surface. The choice that closes doors is the `Text` type and where it resolves. Fluent against gettext matters less, and it can be revisited.

The first returns arrive in English, before any translator is involved. Bidi-safe names close a spoof Dolphin has carried since 2010. Typed errors replace English parsed back, ids replace submenus joined by their titles, and one size convention replaces three. After that, code stops being the limit. The scarce resource is translations that someone has reviewed: a handful of languages kept current by people who speak them, all of them left-to-right until gpui can mirror a window.
